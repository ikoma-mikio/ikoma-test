# CLAUDE.md

このファイルは Claude Code への指示書です。このプロジェクトで作業する際は、以下の方針を守ってください。

## プロジェクト概要

詳細な仕様は @SPEC.md を参照してください。
現在のタスク進捗は @TASKS.md を参照してください。

このプロジェクトは、青山学院大学社会情報学部の学生が履修登録時に感じる「授業同士のつながりが見えにくい」「研究室や進路に向けた4年間の履修ルートが分からない」という課題を解決するための MVP です。

プロダクト名は仮で **履修ワークツリーAI** とします。

重要なのは、単なる時間割アプリではなく、授業・研究室・進路・履修条件をつなげて可視化し、生成AIが学生の目的に合わせて履修ルートを説明するサービスとして作ることです。

## 技術スタック

### MVP 方針

- **フロントエンド**: React 18 / TypeScript / Vite
- **スタイリング**: Tailwind CSS
- **データ管理**: 静的 JSON または CSV
- **グラフ表示**: MVPでは SVG / CSS / React コンポーネントで実装
- **生成AI**: OpenAI API 等の外部AI、または発表用のモック応答
- **テスト**: Vitest（必要に応じて）/ Playwright（画面確認用）
- **パッケージマネージャー**: pnpm

### MVP では原則作らないもの

- ログイン機能
- 本格的なバックエンド
- PostgreSQL などのDB
- 履修登録システムとの連携
- 全学部・全授業対応

発表課題の目的は「最小限で価値を検証できるサービス」なので、最初は静的データを使ったデモでよいです。

## プロダクト設計ルール

- 中心価値は「履修登録を楽にする」ではなく、「4年間の学びの見通しを立てる」こと。
- 楽単探索を中心にしない。扱う場合は「学習負荷を可視化し、無理のない履修計画を立てる」と表現する。
- AIに自由回答をさせすぎない。登録済みの授業データ、授業間リンク、研究室・進路データを根拠に回答させる。
- AI回答には「どの授業データに基づく説明か」が分かるようにする。
- 公式情報と未確認情報を混ぜない。口コミや負担感は「学生アンケート由来」と明示できる形にする。
- 360度の複雑な可視化は将来案とし、MVPでは2Dのワークツリーまたはネットワーク図を優先する。

## コーディングルール

### 全般

- 既存のコードスタイルに合わせること。新しいパターンを勝手に導入しない。
- 変更は最小限にし、タスクに関係ないリファクタリングは行わない。
- コメントは「なぜ」を書く。「何を」はコードから読めるため書きすぎない。
- 発表で見せる画面を優先し、裏側の作り込みに時間を使いすぎない。

### TypeScript

- `any` 型は使わない。型が不明な場合は `unknown` を使い、型ガードで絞り込む。
- 授業、リンク、研究室、進路目標、AI回答には必ず型を定義する。
- データの欠損を想定し、未登録の前提科目や関連情報があっても画面が壊れないようにする。

### React

- 関数コンポーネントのみ使用する。
- 状態管理は `useState` / `useMemo` / `useReducer` を基本とする。
- グラフ表示、目標選択、AI相談パネル、履修プラン表示は責務を分ける。
- プレゼン時に一目で伝わるように、視覚的な状態を明確にする。
  - 取得済み: 緑
  - 目標ルート上: 黄色または青
  - 前提不足: グレー
  - 負担が重い傾向: 控えめな赤い縁取り

### データ

- MVPでは `src/data/*.json` を正とする。
- 授業データには最低限、授業ID、授業名、領域、推奨学年、説明、前提科目、関連目標を含める。
- 授業間リンクには、リンク元、リンク先、リンク種別、理由、重要度を含める。
- データ更新は「教員または運営者がスプレッドシートで更新できる」前提で設計する。

### 生成AI

- AIは学生の目的に合わせて履修ルートの理由を説明する役割に限定する。
- AIに渡す情報は、選択中の目標、取得済み授業、関連授業、授業間リンクに絞る。
- 登録されていない情報について断定しない。
- 発表用のMVPでは、API接続が未完成でも、固定データに基づくモック応答で価値検証できる形にする。

## やってほしくないこと

- 勝手に依存パッケージを追加しない。新しいライブラリが必要な場合は先に提案する。
- `npm install` ではなく `pnpm install` を使う。
- MVP段階で認証、DB、管理画面、全学部対応を作り込まない。
- 楽単探索をメイン機能として打ち出さない。
- AIに公式シラバスのような断定的回答をさせない。
- `.env` や API キーをコミットしない。
- `git push --force` や `git reset --hard` を勝手に実行しない。

## 作業フロー

1. タスクを受け取ったら、まず @SPEC.md と @TASKS.md を確認する。
2. 画面・データ・AI・検証のどれに関する作業かを切り分ける。
3. 実装前に短く方針を出す。
4. 実装後は可能な範囲で `pnpm typecheck`、`pnpm lint`、`pnpm test` を実行する。
5. 画面変更がある場合は、発表で見せる主要画面が崩れていないか確認する。
6. 作業完了後、@TASKS.md の該当タスクを更新する。

## よく使うコマンド

```bash
# 依存関係インストール
pnpm install

# 開発サーバー起動
pnpm dev

# 型チェック
pnpm typecheck

# Lint
pnpm lint

# テスト
pnpm test

# ビルド
pnpm build
```
